## 1. Overview

Django REST backend for a single-location Iranian fast-food restaurant. Two fully
separate API surfaces:

| Area | Prefix | Audience | Auth |
| --- | --- | --- | --- |
| Storefront | `/api/v1/storefront/` | customers | OTP → JWT (`Authorization: Bearer`) or Django session |
| Backoffice | `/api/v1/backoffice/` | staff/manager | password login → **session only** (JWT rejected by design) |

Features: menu with category/product/two-layer add-ons, lucky-wheel source list,
OTP login, order registration with price snapshots, Zarinpal v4 payments with
idempotent verification, live kitchen POS (polling), CRM (customer 360 + notes +
LTV), CMS (restaurant settings / site sections / media with WebP), manual
cancel → awaiting_refund → refunded flow, Celery beat auto-cancel of unpaid orders.

User-facing messages are **Persian (fa-ir)**; code and comments are English.
Django admin is **not installed** (decision D5). There is no router/viewset layer —
every endpoint is an explicit `APIView` plus explicit `path()` entries.

## 4. Architecture and conventions

Request path: `config.urls` → area urls → module urls → `APIView` → serializer
validation → `services.*` (writes) or `selectors.*` (reads) → ORM → `Response`.

Conventions actually enforced in the code:

- Reads in `selectors.py`, writes in `services.py`; views contain no business logic
  and no `.objects.filter()` calls.
- `@transaction.atomic` on multi-table writes and state transitions.
- `transaction.on_commit(...)` for side effects (Celery `.delay`, cache invalidation).
- **Soft delete**: `common.models.BaseModel` gives `created_at`, `updated_at`,
  `deleted_at`; `objects` = `SoftDeleteManager` (alive only), `all_objects` = plain
  manager; `delete()` delegates to `soft_delete()`; `SoftDeleteQuerySet` adds
  `.alive()`, `.dead()`, `.hard_delete()`.
- Unique constraints are partial on `deleted_at__isnull=True`, so slugs/keys are
  reusable after soft delete.
- Errors: raise `BusinessException` subclasses (`common/exceptions.py` plus per-app
  `exceptions.py`); `common.exception_handler.custom_exception_handler` renders
  `{"success": false, "error": {"code", "message", "details"}}`. Success payloads are
  unwrapped.
- Cache keys via `common.cache.make_cache_key(area, scope)` → `area:scope:v1`;
  the backend prepends `KEY_PREFIX="fastfood"` and its own version.
- Money is integer toman everywhere; no `Decimal` in the codebase (D1).
- `Asia/Tehran`, `USE_TZ=True`; "today" always via `timezone.localdate()`.

`common.views.BackofficeAPIView` hard-codes
`authentication_classes=[SessionAuthentication]` and
`permission_classes=[IsStaffUser]`; every backoffice view subclasses it and
re-declares the same permission. CSRF is therefore required on backoffice
POST/PATCH/DELETE and on storefront session writes; JWT clients are CSRF-exempt.

  `addons = M2M(AddOn, through=ProductAddOn)`.

- `orders.Order(BaseModel)`: customer FK (PROTECT), status, payment_status,

  subtotal/delivery_fee/total_amount, prep_time_minutes, expected_ready_at,
  paid_at, notes_to_kitchen, is_printed/printed_at, daily_number +
  daily_number_date (partial unique on the pair), expires_at, cancellation fields,

- `orders.OrderItem(BaseModel)`: product FK (PROTECT) + name/unit-price snapshots,

- `orders.OrderItemAddOn(BaseModel)`: addon FK (PROTECT) + name/unit-price

- `payments.Payment(BaseModel)`: order FK (PROTECT), amount, status ∈
  PENDING/SUCCEEDED/FAILED/CANCELED, `authority` (unique while alive), ref_id,

## 8. Critical business rules (as implemented)

**Order state machine** (`apps/orders/services.py`):
`PENDING_PAYMENT` → (payment verified) `PROCESSING` → (manager) `READY` →
(manager) `COMPLETED`; `CANCELED` from any non-final state by a manager, or
automatically for expired unpaid orders.

- `create_order`: restaurant must be open; `DELIVERY` requires an address owned by
  the customer (fee = in/out-of-zone fee; `PICKUP` = 0); each product must exist, not
  be HIDDEN, be AVAILABLE, and have an active category; each add-on must exist for
  that product and be `is_available`; add-on quantity must be
  `<= ProductAddOn.max_quantity` (**`min_quantity` is never enforced**);
  `expires_at = now + 15 min`; `prep_time = max(product prep) + buffer`.
- Snapshots: `product_name_snapshot`, `unit_price_snapshot`, `addon_*_snapshot`,
  `delivery_address_snapshot` protect historical invoices.
- `mark_order_paid`: locks the order, requires `PENDING_PAYMENT`, sets `paid_at`,
  `PROCESSING`, `PAID`, `expected_ready_at = paid_at + prep`, `is_printed=False`,
  assigns the daily number, then `on_commit` manager SMS.
- Daily number: Redis `INCR order_seq:<localdate>` (48 h TTL on first increment),
  persisted with a partial unique constraint and a retry loop (see §14 #4).
- `update_prep_time` (PROCESSING/READY only): `expected_ready_at = paid_at +
  new_minutes` (anchored to payment, not now).
- Manager cancel: PAID → `AWAITING_REFUND`, UNPAID stays UNPAID; blocked when
  already CANCELED/COMPLETED/AWAITING_REFUND/REFUNDED.
- `record_refund`: only from `AWAITING_REFUND`; stores card number, tracking code,
  `refunded_at`, `refunded_by`.
- Auto-cancel: beat every 60 s cancels `PENDING_PAYMENT` orders past `expires_at`
  (`cancellation_reason="auto: payment timeout"`).
- Live POS: `get_live_orders()` = PROCESSING + READY ordered by `expected_ready_at`;
  `mark_order_printed` is idempotent; printing/alarm is frontend responsibility.
- Lucky wheel: AVAILABLE + `is_main_dish` + active category; the backend only
  supplies the list (spin logic is frontend), cached per category slug.
- Menu: active categories with products excluding HIDDEN (OUT_OF_STOCK shown),
  cached 1 h as plain dicts (not pickled models).

**Payments** (`apps/payments/services.py`, `zarinpal.py`):
`ZarinpalClient` uses `urllib`, v4 endpoints (`sandbox`/`payment` host switch), and
raises at construction when `ZARINPAL_MERCHANT_ID` is empty.
`start_payment_for_order` requires PENDING_PAYMENT + UNPAID + not expired, re-runs
`revalidate_order_for_payment` (open, products AVAILABLE, add-ons available),
creates a PENDING `Payment`, returns `{payment_url, authority, amount}`.
`verify_payment` is `@transaction.atomic`: locks the payment row, returns early when
SUCCEEDED (idempotent), marks FAILED on `Status != OK` or Zarinpal rejection, and on
success stores ref_id then calls `mark_order_paid` in the same transaction.
`retry_payment` re-checks state/expiry and delegates to `start_payment_for_order`
(the view verifies ownership first). `reverify_pending_payments` (beat, 300 s)
re-verifies PENDING payments older than 3 min.

**OTP** (`apps/accounts/otp.py`, `services.py`): 6-digit `secrets.randbelow`, stored
as JSON `{"code": ...}` under `otp:code:<phone>:v1` with a 120 s TTL, compared with
`hmac.compare_digest`, deleted on success (a wrong code leaves the OTP alive).
`normalize_phone` accepts `+98…`, `0098…`, `98…`, `9…` and normalizes to `09…`.
`verify_otp` get-or-creates the customer, then rejects blocked/inactive accounts.
Throttles (`apps/accounts/throttles.py`): `otp_request` 5/h, `otp_verify` 10/h,
`staff_login` 10/h, keyed on `phone:client_ip`.

`staff_login` normalizes the phone, uses `select_for_update()`, rejects
blocked → inactive → not staff → bad password (credential errors do not reveal which
step failed), updates `last_login`; the view then calls Django `login()` and returns
the user plus a CSRF token.

**JWT** (`apps/accounts/tokens.py`): `RefreshToken.for_user`,
`ROTATE_REFRESH_TOKENS=True`, `BLACKLIST_AFTER_ROTATION=True`, lifetimes from
`JWT_ACCESS_LIFETIME_MINUTES` (60) / `JWT_REFRESH_LIFETIME_DAYS` (7).
`OTPVerifyView` returns `{user, access, refresh}` **and** creates a session.

**CMS caching**: `cms:restaurant_settings:v1` (1 h; invalidated on commit by
`update_restaurant_settings`), `cms:site_section_<key>:v1` and
`cms:site_sections_all:v1` (invalidated by `upsert_site_section`). Missing sections
fall back to `DEFAULT_SITE_SECTION_CONTENT`; valid keys never 404.

## 9. External integrations

- **Zarinpal v4** (`apps/payments/zarinpal.py`): request/verify/StartPay over
  `urllib.request`, 15 s timeout, codes 100 (fresh) and 101 (already verified)
  treated as success.
- **sms.ir bulk API** (`common/sms.py`, `POST https://api.sms.ir/v1/send/bulk`,
  `x-api-key`, 10 s timeout). If `SMS_IR_API_KEY` or `SMS_IR_SENDER` is empty the
  message is only logged and `True` is returned — this is how OTP appears in the dev
  console.
- **Redis**: cache backend, Celery broker/results, and the daily-number counter.
- No payment reconciliation or refund API: refunds are recorded manually (card
  number + tracking code) and money is returned outside the system.

## 11. Security posture

- Public: OTP request/verify, token refresh/logout, CSRF, catalog, CMS reads, and the
  Zarinpal callback (which re-verifies the supplied `Authority` server-side).
- Storefront object access is always scoped by `customer_id=request.user.pk`
  (`selectors.get_order_for_customer`), so cross-customer reads return
  `ORDER_NOT_FOUND`. `PaymentStatusView` additionally checks
  `payment.order.customer_id`.
- Backoffice requires `is_staff` + session; JWT is rejected at the authentication
  class level (test `test_jwt_rejected_on_backoffice`).
- Uploads: `ImageUploadSerializer` / `MediaAssetSerializer.validate_file` cap size at
  10 MB; Pillow decodes. Media is served by Django only when `DEBUG`.
- OTP comparison is constant-time and OTPs live only in Redis.
- No secrets in tracked files (`.env` absent; `.env.example` has placeholders).
- Residual risks: hard-coded DEBUG, unthrottled callback, service-level
  `retry_payment` not customer-scoped (the view compensates), soft-deleted products
  still referenced with PROTECT (see §14).

## 12. Key end-to-end workflows

1. **Customer login**: `POST otp/request/` → normalize → store OTP → Celery
   `send_otp_sms` (logged in dev) → `POST otp/verify/` → compare, delete OTP,
   get-or-create customer → session + JWT pair.
2. **Place order**: `POST orders/` → `create_order` (open check → address/ownership →
   delivery fee → prep time → `Order` row → items/add-ons with snapshots →
   subtotal/total). Response is `PENDING_PAYMENT`/`UNPAID`.
3. **Pay**: `POST payments/request/` (ownership) → revalidation → Zarinpal request →
   `Payment(PENDING)` → redirect URL. Return to
   `GET payments/callback/?Authority&Status` → `verify_payment` → Zarinpal verify →
   `Payment(SUCCEEDED)` + `mark_order_paid` (PROCESSING / daily number / manager SMS)
   → redirect to `PAYMENT_FRONTEND_RESULT_URL` (or JSON with `?format=json`).
4. **Kitchen**: staff polls `orders/live/`; `is_printed=False` rows trigger
   print+alarm; `mark-printed` → `mark-ready` (customer SMS) → `mark-completed`.
   Prep-time overrides recompute the ETA and notify the customer.
5. **Cancel/refund**: `cancel/` → `AWAITING_REFUND` → manual card transfer →
   `refund/` with card+tracking → `REFUNDED`.
6. **Timeout**: beat task cancels unpaid orders after 15 min; another re-verifies
   stale PENDING payments.
7. **CRM/CMS**: staff edit customer flags/notes; CMS edits invalidate cache keys on
   commit so storefront reads refresh on the next request.

## 14. Known defects / technical debt (verified 2026-11-24)

> **Status update (2026-11-24, discovery phase):** items **1, 2, 4, 6, 9 and 10**
> below are fixed, as are the `settings_sqlite.py`, seed-migration and `DEBUG`
> documentation drifts in §15. The remaining items are still open.

### Critical

1. **`settings.REDIS_URL` does not exist.** `config/settings.py` passes
   `config("REDIS_URL", ...)` inline into `CACHES`, while
   `common/redis_client.get_redis()` reads `settings.REDIS_URL`. Verified:
   `hasattr(settings, "REDIS_URL") == False`. `_assign_daily_number()` therefore
   raises `AttributeError` inside `mark_order_paid`, so **every successful payment
   rolls back** and orders never reach PROCESSING. Only the test suite is immune
   (conftest injects the attribute). **Fixed:** `REDIS_URL` is declared at module
   level, the cache backend is selected by `CACHE_BACKEND` (locmem by default), and
   `_assign_daily_number` falls back to a DB `MAX(daily_number)` sequence when Redis
   is unreachable, so a payment no longer rolls back on a fresh dev machine.
2. **No seeded `RestaurantSettings` row.** No `0002_seed_restaurant_settings`
   migration exists (README claims one) and `cms_restaurantsettings` is empty in
   `db.sqlite3`. `selectors.get_restaurant_settings()` calls
   `RestaurantSettings.objects.get(pk=1)`, raising `DoesNotExist` → unhandled 500 for
   storefront `restaurant-status`, **all order creation**, payment start, and
   backoffice settings GET/PATCH on a fresh database. **Fixed:** migration
   `cms.0002_seed_restaurant_settings` seeds `pk=1`, and
   `get_restaurant_settings()` / `update_restaurant_settings()` use
   `get_or_create` so databases migrated earlier are also safe.

### High

3. **Backoffice routing is broken** (§7): auth under `/backoffice/crm/auth/...` and
   orders under `/backoffice/orders/orders/...`, while the README, frontend contract,

## 16. Product discovery (search / filter / sort / autocomplete)

Backend-only feature; the frontend is untouched. Entry points:

| Method | Path | Auth | Throttle |
| --- | --- | --- | --- |
| GET | `/api/v1/storefront/catalog/products/` | public | `catalog_search` 120/min |
| GET | `/api/v1/storefront/catalog/suggestions/` | public | `catalog_suggest` 120/min |

### Architecture

```
view (validate params)  →  selectors.search_public_products()
                              ├─ get_public_product_queryset()      visibility
                              ├─ _category_subtree_ids()            hierarchy
                              ├─ search.apply_filters()             filters
                              ├─ search.build_search_filter()       search
                              └─ search.apply_ordering()            sort/popularity
                           selectors.suggest_public_products_with_correction()
                              └─ same pipeline + one fuzzy fallback
```

- `apps/catalog/search.py` — the single search implementation: normalization,
  Arabic/Persian variants, `Q` construction, relevance ranking, allowlisted
  ordering. No ORM writes, no view logic.
- `apps/catalog/selectors.py` — `get_public_product_queryset`,
  `search_public_products`, `suggest_public_products`.
- `apps/catalog/apis/storefront/{serializers,views,urls}.py` — request validation,
  pagination and response shaping only.
- `apps/catalog/throttles.py` — per-IP throttles for both endpoints.

### Data model additions (`catalog.0002_category_parent_product_compare_at_price_and_more`)

| Field | Type | Meaning |
| --- | --- | --- |
| `Product.compare_at_price` | positive int, null | original/pre-discount price; null = not discounted; DB check `> price` |
| `Product.stock_quantity` | positive int, null | counted stock; null = untracked |
| `Category.parent` | FK self, null, `PROTECT` | optional hierarchy; `related_name="children"` |

Indexes: `catalog_product_price_idx` (price sorting/filtering) and
`catalog_product_cat_status_idx` (category + visibility). Constraints:
`product_compare_at_price_gt_price`, `category_parent_not_self`. Derived
read-only fields exposed by the storefront: `discount_percent`, `is_discounted`,
`is_in_stock`; `Category` also exposes `parent_id`. The backoffice product
write/update serializers accept `compare_at_price` and `stock_quantity`, and
category write/update serializers accept `parent_id` (cycle/self-parent rejected
by `catalog.services`).

### Visibility rules (single source of truth)

`get_public_product_queryset()` = alive product (`objects`, i.e. `deleted_at IS
NULL`) + `status != HIDDEN` + category `is_active=True` and not soft-deleted.
`OUT_OF_STOCK` products stay discoverable (same rule as the storefront menu) and
are flagged by `status` in the payload so the frontend can disable them. Neither
search, filters, nor autocomplete can reach a HIDDEN product or an inactive
category. Category filters resolve the active subtree, so filtering a parent
includes its children unless `include_subcategories=false` is sent.

### Searchable fields and normalization

Fields: `name`, `slug`, `description`, `category__name`. Matching is
`icontains` (case-insensitive for ASCII on SQLite; Persian is caseless).

The query (never the stored data) is normalized: Arabic Yeh `ي` → Persian `ی`,
Arabic Kaf `ك` → Persian `ک`, Arabic-Indic (`٠١٢…`) and Persian (`۰۱۲…`) digits →
ASCII, zero-width/non-joiner/tatweel characters removed, whitespace collapsed and
trimmed, truncated to 100 chars. Because stored rows are not rewritten, the
normalized term is expanded to up to 4 letter variants (Persian and/or Arabic
Yeh/Kaf) and every variant is OR-ed across the four fields.

Search is **word-based**: the query is split into at most 8 words and every word
must match at least one field (AND across words, OR across fields). This lets
"پیتزا مخصوص" match "پیتزا مخصوص فرنگی" and lets different words match the name,
description and category independently. Each word is also expanded with the
built-in Persian food synonym groups in `search.SYNONYM_GROUPS` (e.g.
برگر/همبرگر, مرغ/چیکن/جوجه, نوشابه/نوشیدنی/کوکاکولا, سیب‌زمینی/فرای) plus the
optional `settings.CATALOG_SEARCH_SYNONYMS` override. Empty/blank queries apply
no search filter.

Ranking (`build_relevance_ordering`): exact name (5) > name prefix (4) > name
substring (3) > slug/category-name/description substring (2) > 0, then
`display_order`, `name`, `pk` for deterministic pagination.

**Typo tolerance (autocomplete only):** when a suggestion query returns zero rows
and `CATALOG_SEARCH_FUZZY_ENABLED` is true, `correct_search_term()` compares each
query word with the product-name vocabulary (cached, invalidated with the catalog
cache) using `difflib` at `CATALOG_SEARCH_FUZZY_CUTOFF` (default 0.80). One
corrected term is tried; if it matches, the response carries `did_you_mean`. The
normal path costs one query and never scans the catalog. The product listing does
not silently broaden results this way.

### Filters (all optional, combinable)

| Param | Type | Behaviour |
| --- | --- | --- |
| `q` | string (≤100) | word-based search with synonyms, see above |
| `category` | slug | filter by active category subtree; unknown/inactive → 404 `CATEGORY_NOT_FOUND` |
| `category_id` | int ≥1 | same by PK; non-numeric → 400 |
| `include_subcategories` | bool, default true | false → only products directly in the selected category |
| `min_price` | int 0…1e9 | inclusive `price >=` |
| `max_price` | int 0…1e9 | inclusive `price <=`; `min > max` → 400 |
| `available` | bool | raw flag: `1` → `status=AVAILABLE`; `0` → `status=OUT_OF_STOCK`; omitted → both |
| `in_stock` | bool | effective: AVAILABLE **and** (stock not tracked or `stock_quantity > 0`) |
| `discount` | bool | `1` → `compare_at_price > price`; `0` → not discounted; omitted → both |
| `is_main_dish` | bool | real `Product.is_main_dish` field |

### Sorting (`sort`, allowlist)

`default` (`display_order`, `name`, `pk`) · `newest` (`-created_at`, `-pk`) ·
`oldest` (`created_at`, `pk`) · `price_asc` (`price`, `display_order`, `pk`) ·
`price_desc` (mirror) · `popularity` (`-sales_count`, default order) ·
`relevance` (falls back to `default` without a `q`).
When `q` is present and no `sort` is given, relevance is used. Arbitrary field
names are impossible: unknown values → 400.

`popularity` is computed at query time by `search.annotate_sales_count()`:
`SUM(OrderItem.quantity)` over orders with `payment_status=PAID` and status in
(PROCESSING, READY, COMPLETED). Refunded/canceled orders drop out automatically,
so no denormalised counter or signal can drift. It costs one LEFT JOIN + GROUP BY
and is only applied when requested.

### Pagination

Existing `LimitOffsetPagination` (`PAGE_SIZE=20`) only. `limit`/`offset` are
validated by the paginator; `next`/`previous` are rebuilt from the request, so all
filter and sort parameters survive paging. Ordering always has a unique
tie-breaker, so pages never overlap.

### Response shapes

List (`200`):
```json
{
  "count": 2, "next": null, "previous": null,
  "results": [
    {"id": 1, "name": "Burger", "slug": "burger", "description": "",
     "price": 180000, "compare_at_price": 220000, "discount_percent": 18,
     "is_discounted": true, "stock_quantity": 25, "is_in_stock": true,
     "status": "AVAILABLE", "is_main_dish": true,
     "prep_time_minutes": 10, "image_url": null,
     "category": {"id": 1, "name": "Pizzas", "slug": "pizzas",
                  "parent_id": null, "description": "", "image_url": null}}
  ]
}
```

`price` remains the effective selling price (and the value orders snapshot);
`compare_at_price` is the optional pre-discount price; `discount_percent` is
derived. `stock_quantity = null` means stock is not tracked.

Suggestions (`200`) —
`{"results": [{id, name, slug, price, compare_at_price, discount_percent, is_in_stock, status, image_url}], "did_you_mean": null|string}`,
at most `PRODUCT_SUGGESTIONS_MAX_LIMIT` (10) rows; blank `q` → `{"results": [], "did_you_mean": null}`.
The frontend builds the detail URL from `slug` (`/catalog/products/<slug>/`).

Errors use the standard envelope (`400` for invalid parameters via DRF
validation, `404 CATEGORY_NOT_FOUND` for unknown/inactive categories).

### Performance

- Base queryset uses `select_related("category")`; the search join is
  many-to-one, so no `distinct()` and no row duplication.
- List: 2 queries (count + page) on the normal path; `sort=popularity` adds one
  LEFT JOIN + GROUP BY instead of a per-row query.
- Suggestions: 1 query on the normal path; `.select_related(None).only(...)` loads
  only the returned columns (`.only()` cannot coexist with `select_related`). A
  zero-result query may add one `exists()` check plus, when fuzzy is enabled, one
  cached vocabulary read and one corrected query.
- Indexes added in `catalog.0002`: `price` and `(category, status)`. SQLite cannot
  use a B-tree index for leading-wildcard `icontains`, so search itself still
  scans; scale guidance (PostgreSQL FTS/pg_trgm) remains a recommendation.
- No caching is applied to search results (combinatorial key space); only the
  autocomplete vocabulary is cached (1 h, invalidated with the catalog cache).

### Decisions and limitations

- **Discounts are modelled as `compare_at_price`.** `Product.price` stays the
  effective selling price, so existing order snapshots and totals do not change.
  The DB constraint `product_compare_at_price_gt_price` and the backoffice
  services reject `compare_at_price <= price`; refund/order logic is untouched.
- **Stock is counted but not decremented at checkout.** `stock_quantity` (null =
  untracked) drives the `in_stock` filter/flag; order creation still relies on
  `status`, so reserving/decrementing stock and oversell protection are a later
  order-domain change (needs reservation + cancellation restore).
- **No variant model.** Product variants are not part of the current order model
  (`OrderItem` references a single `Product` and snapshots its price); adding
  variants only to the catalog would let customers choose an option the order
  cannot record. Sizes remain separate products (decision D20) until a
  variant-aware order-item schema is agreed.
- **Hierarchy is parent/child with cycle protection.** Filtering resolves active
  descendants in Python (one small query) rather than a recursive CTE, so it is
  identical on SQLite and PostgreSQL. Deactivating a parent does **not**
  auto-deactivate children; the backoffice must deactivate the subtree (menu
  semantics are unchanged).
- **Typo tolerance is a bounded autocomplete fallback, not stemming.** It
  corrects words against product-name vocabulary with `difflib`; it is not
  Levenshtein in SQL and not a replacement for a search engine.
- SQLite `LIKE` is case-insensitive for ASCII only; Persian has no case, so this
  is acceptable, but accent-insensitive Latin matching would need a real search
  backend.
- ZWNJ is stripped from the query; a query written with a half-space may not
  match stored text that uses one, and vice versa (data is never rewritten).
  Word-based AND matching mitigates this ("سیب زمینی" matches "سیب‌زمینی").
- `tests/test_product_discovery.py` predates these additions: it still expects
  `discount=1` to be rejected and has no coverage for `in_stock`,
  `include_subcategories`, `popularity` or `did_you_mean`. It was intentionally
  **not** modified or executed in this phase; it must be updated when the test
  infrastructure is revived.

## 17. Rules for future work on this repo

1. Read the module's `selectors`, `services`, and migrations before changing it;
   preserve the read/write split and `BaseModel` soft-delete semantics.
2. Reuse `common.exceptions` subclasses and the existing error envelope — never raise
   bare exceptions for business rules or return DRF's default error shape.
3. Money/state transitions go inside `@transaction.atomic`, with `on_commit` for
   cache/SMS side effects; keep snapshots on order rows.
4. Cache keys go through `make_cache_key`, and every derived key (including per-slug
   variants) must be invalidated.
5. Do not change existing URL paths, serializer field names, or status codes without
   explicit approval — the frontend and tests depend on them.
6. Work on payments/order state must cover the happy path **and** the
   expired/canceled/duplicate-callback paths; gaps #5, #6, #7 all live there.
7. New behaviour should ship with tests, but state honestly that the suite is not
   trustworthy until the routing and seed issues are fixed; never report a green run
   you did not get.
8. Update this file and the README when behaviour or paths change; avoid docs that
   merely restate the code.
