# جریان‌های کاربر و سناریوهای ورود — فروشگاه FastFood

**دامنه سند:** فقط بخش Storefront (مشتری) — آدرس پایه: `/api/v1/storefront/`
**مبنا:** کد پیاده‌سازی‌شده در `apps/accounts/`, `apps/catalog/`, `apps/orders/`, `apps/payments/`, `apps/cms/`, `common/permissions.py` و `config/api_urls_storefront.py`
**آخرین به‌روزرسانی:** ۲۷ نوامبر ۲۰۲۶

این سند از روی رفتار واقعی کد نوشته شده است، نه از روی طرح اولیه. هرجا مستندات قدیمی‌تر (مثل `README.md`) با کد اختلاف داشته باشد، مبنای این سند کد است. برای نمونه:

- ورود مشتری **فقط JWT** است و هیچ Session یا کوکی ورودی ساخته نمی‌شود.
- endpointای به نام `GET /auth/csrf/` در Storefront وجود ندارد (CSRF فقط در Backoffice معنا دارد).
- جست‌وجو با PostgreSQL Full-Text + Trigram انجام می‌شود و «ایندکس توکن دستی» وجود ندارد.
- دسته‌بندی‌ها **تخت** هستند؛ فیلد زیردسته یا `include_subcategories` وجود ندارد.

## ۰. قواعد مشترک

### ۰.۱ احراز هویت

| موضوع | رفتار واقعی |
| --- | --- |
| کلاس پایه | `StorefrontAPIView` با `authentication_classes = [JWTAuthentication]` |
| هدر | `Authorization: Bearer <access_token>` |
| Session | پذیرفته **نمی‌شود**؛ حتی اگر کارمند در Backoffice سشن داشته باشد، همان کوکی روی Storefront نادیده گرفته می‌شود |
| CSRF | برای هیچ endpoint فروشگاه لازم نیست |
| permission پیش‌فرض | `IsActiveCustomer`: کاربر باید احراز هویت شده، `is_active=True` و `is_blocked=False` باشد |
| endpointهای عمومی | `AllowAny` هستند ولی همچنان فقط JWT را می‌شناسند (اثری ندارد چون توکنی لازم نیست) |

### ۰.۲ قالب پاسخ خطا

همه پاسخ‌های غیر ۲xx یک پوشش ثابت دارند:

```json
{
  "success": false,
  "error": {
    "code": "OTP_INVALID",
    "message": "کد تایید نادرست است.",
    "details": null
  }
}
```

- پاسخ موفق **پوشش ندارد** و داده مستقیم برگردانده می‌شود.
- پاسخ `204` بدنه ندارد.
- خطاهای اعتبارسنجی سطح serializer معمولاً `400` با `code: "INVALID"` هستند.
- خطاهای قاعده کسب‌وکار (کلاس‌های `BusinessException`) کد اختصاصی و وضعیت مشخص خودشان را دارند (اغلب `422`).

### ۰.۳ محدودیت نرخ (Throttle)

| scope | نرخ | روی چه endpointهایی | کلید |
| --- | --- | --- | --- |
| `otp_request` | ۵ بار در ساعت | `POST /auth/otp/request/` | شماره خام + IP کلاینت |
| `otp_verify` | ۱۰ بار در ساعت | `POST /auth/otp/verify/` | شماره خام + IP کلاینت |
| `catalog_search` | ۱۲۰ بار در دقیقه | `GET /catalog/products/` | IP کلاینت |
| `catalog_suggest` | ۱۲۰ بار در دقیقه | `GET /catalog/suggestions/` | IP کلاینت |
| `staff_login` | ۱۰ بار در ساعت | فقط Backoffice | — |

نکات دقیق:

- شماره در کلید throttle **نرمال‌سازی نمی‌شود**؛ پس `+989121234567` و `09121234567` دو کلید جدا هستند و سهمیه را جدا مصرف می‌کنند.
- شمارش قبل از اجرای view انجام می‌شود؛ یعنی درخواست موفق هم از سهمیه کم می‌کند.
- پاسخ عبور از سهمیه: `429` با `code: "THROTTLED"`، هدر `Retry-After` و جزئیات شامل ثانیه‌های باقی‌مانده (متن جزئیات انگلیسی است).

### ۰.۴ منبع پیکربندی رستوران

ساعت کاری، تعطیلی موقت، هزینه ارسال درون/برون‌منطقه، حداقل مبلغ ارسال، هزینه بسته‌بندی و بافر زمان آماده‌سازی از مدل تک‌نمونه‌ای `RestaurantSettings` (pk=1) خوانده می‌شوند و از طریق `GET /cms/restaurant-status/` برای فرانت قابل مشاهده‌اند. مقادیر پیش‌فرض مدل: ساعت ۱۱:۰۰ تا ۰۱:۰۰، ارسال درون‌منطقه ۵۰٬۰۰۰، برون‌منطقه ۱۰۰٬۰۰۰، حداقل ارسال ۰، بسته‌بندی ۰ و بافر ۵ دقیقه. مقادیر واقعی استیجینگ با دستور seed و پنل مدیریت تعیین می‌شوند.

### ۰.۵ کشف و کش

| داده | TTL | نحوه بی‌اعتبارسازی |
| --- | --- | --- |
| منوی فروشگاه | ۱ ساعت | هر نوشتن در کاتالوگ (دسته/محصول/افزودنی) پس از commit |
| گردونه شانس (کل و هر دسته) | ۱ ساعت | همان |
| Upsell | ۱ ساعت | همان |
| نتایج جست‌وجو | ۶۰ ثانیه (قابل تنظیم) | افزایش شماره نسل کش در هر نوشتن کاتالوگ |
| پیشنهادهای Autocomplete | ۱۲۰ ثانیه (قابل تنظیم) | همان |
| تنظیمات رستوران و بخش‌های سایت | ۱ ساعت | به‌روزرسانی از Backoffice پس از commit |

پیامد کاربری: تغییر قیمت یا اتمام موجودی ممکن است تا پایان TTL در فهرست‌های cache‌شده دیده نشود؛ اما در **ثبت سفارش** همیشه وضعیت لحظه‌ای دیتابیس اعتبارسنجی می‌شود.

## ۱. احراز هویت و همه سناریوهای ورود

### ۱.۰ مدل ذهنی درست از ورود

این پروژه «ثبت‌نام» کلاسیک ندارد. هویت مشتری فقط با **شماره موبایل تأییدشده با OTP** ساخته می‌شود:

1. درخواست OTP → کد ۶ رقمی با اعتبار **۱۲۰ ثانیه** در Redis (کلید cache) ذخیره می‌شود.
2. تأیید OTP → اگر مشتری با آن شماره وجود نداشته باشد، **به‌صورت خودکار** ساخته می‌شود.
3. پاسخ تأیید شامل `access` و `refresh` است.
4. **هیچ Session یا کوکی ورودی ساخته نمی‌شود**؛ کلاینت باید توکن‌ها را خودش نگه دارد.
5. رمز عبور مشتری `unusable` است؛ ورود با رمز فقط برای کارکنان در Backoffice است.

### سناریو A — کاربر جدید: ثبت‌نام + ورود

#### گام ۱ — ورود به‌عنوان مهمان

کاربر بدون توکن صفحات عمومی را می‌بیند:

- `GET /cms/restaurant-status/`
- `GET /cms/site-sections/`
- `GET /catalog/menu/`
- `GET /catalog/products/` و `GET /catalog/products/<slug>/`
- `GET /catalog/lucky-wheel/`
- `GET /catalog/upsell/`

همه این‌ها `AllowAny` هستند و توکن لازم ندارند.

#### گام ۲ — درخواست کد

```
POST /api/v1/storefront/auth/otp/request/
Content-Type: application/json

{ "phone": "09121234567" }
```

پاسخ موفق:

```json
{
  "message": "کد تایید ارسال شد.",
  "expires_in": 120
}
```

در همین لحظه:

- شماره با `normalize_phone` استاندارد می‌شود.
- یک کد ۶ رقمی با `secrets` تولید می‌شود (قابل پیش‌بینی نیست).
- کد در cache با کلید اختصاصی همان شماره و TTL=۱۲۰ ثانیه ذخیره می‌شود (فرمت داخلی JSON: `{"code": "123456"}`).
- ارسال پیامک از طریق تسک Celery `apps.accounts.tasks.send_otp_sms` روی صف `high_priority` انجام می‌شود.
- **هیچ رکورد `Customer` ساخته نمی‌شود.**

#### گام ۳ — نرمال‌سازی شماره (رفتار دقیق)

تابع نرمال‌سازی:

1. همه کاراکترهای غیررقمی حذف می‌شوند (`+`, فاصله، خط تیره، حروف).
2. اگر با `0098` شروع شود، این پیشوند حذف می‌شود.
3. اگر با `98` شروع شود و طول دقیقاً ۱۲ باشد، `98` حذف می‌شود.
4. اگر طول ۱۰ باشد و با `9` شروع شود، یک `0` به ابتدا اضافه می‌شود.
5. نتیجه باید **۱۱ رقم** و با `09` شروع شود، وگرنه خطای `422` با کد `VALIDATION_ERROR` و `details.phone` برمی‌گردد.

نمونه‌های پذیرفته‌شده:

| ورودی | نتیجه |
| --- | --- |
| `09121234567` | `09121234567` |
| `+98 912 123 4567` | `09121234567` |
| `00989121234567` | `09121234567` |
| `989121234567` | `09121234567` |
| `9121234567` | `09121234567` |
| `0912-123-4567` | `09121234567` |

نمونه‌های ردشده: `1234567890`، `0912345` (کوتاه)، `+1 555 0100`، رشته بدون رقم مثل `abc`.

> نکته: چون نرمال‌سازی هم در درخواست و هم در تأیید اجرا می‌شود، کاربر می‌تواند کد را با `+98...` بگیرد و با `09...` تأیید کند؛ هر دو یک کلید و یک حساب هستند.

#### گام ۴ — تأیید کد و ساخت خودکار حساب

```
POST /api/v1/storefront/auth/otp/verify/
Content-Type: application/json

{ "phone": "09121234567", "code": "123456" }
```

پاسخ موفق (`200`):

```json
{
  "user": {
    "id": 12,
    "phone": "09121234567",
    "full_name": "",
    "is_blocked": false,
    "date_joined": "2026-11-27T10:12:00+03:30",
    "created_at": "2026-11-27T10:12:00+03:30"
  },
  "access": "eyJ...",
  "refresh": "eyJ..."
}
```

پشت صحنه به این ترتیب:

1. کد ذخیره‌شده خوانده می‌شود؛ اگر وجود نداشته باشد (منقضی یا درخواست‌نشده) → `400 OTP_EXPIRED`.
2. مقایسه با `hmac.compare_digest` انجام می‌شود (مقاوم به timing attack).
3. در صورت نادرستی → `400 OTP_INVALID` و **کد حذف نمی‌شود**.
4. در صورت درستی → کد **فوراً حذف** می‌شود (یک‌بارمصرف).
5. `Customer` با آن شماره `get_or_create` می‌شود؛ رکورد جدید `is_active=True`, `is_blocked=False` و رمز `unusable` دارد.
6. سپس `is_blocked` و `is_active` بررسی می‌شوند.
7. توکن‌های JWT صادر می‌شوند: `access` (پیش‌فرض ۶۰ دقیقه) و `refresh` (پیش‌فرض ۷ روز).

#### گام ۵ — استفاده از توکن

```
GET /api/v1/storefront/auth/me/
Authorization: Bearer <access>
```

پاسخ پروفایل است. فهرست آدرس‌ها در ابتدا خالی است:

```
GET /api/v1/storefront/auth/addresses/
```

#### حالت‌های مرزی سناریو A

| اتفاق | نتیجه |
| --- | --- |
| شماره نامعتبر | `422 VALIDATION_ERROR` (نه ۴۰۰ ساده) |
| درخواست دوباره OTP برای همان شماره | کد قبلی **بازنویسی** می‌شود و TTL از نو ۱۲۰ ثانیه می‌شود؛ کد قدیمی دیگر معتبر نیست |
| تأیید با کد اشتباه | `400 OTP_INVALID`؛ کد همچنان معتبر است تا TTL |
| تأیید بعد از ۱۲۰ ثانیه | `400 OTP_EXPIRED` |
| تأیید دوباره با همان کد | `400 OTP_EXPIRED` (کد مصرف شده) |
| درخواست OTP و بعد تأیید بدون درخواست | `400 OTP_EXPIRED` |
| ورود با شماره‌ای که حساب blocked دارد | OTP ارسال می‌شود، تأیید کد انجام می‌شود، سپس `403 ACCOUNT_BLOCKED` و توکن صادر نمی‌شود. کد مصرف شده است |
| ورود با حساب `is_active=False` | `403 ACCOUNT_INACTIVE` بعد از مصرف کد |
| تلاش برای ویرایش نام در ثبت‌نام | وجود ندارد؛ `full_name` فقط از CRM پنل مدیریت قابل تغییر است |

> نکته امنیتی/تجربه کاربری: درخواست OTP برای شماره‌های مسدود هم پیامک می‌فرستد و پاسخ یکسان است؛ این کار از افشای وجود/عدم وجود حساب جلوگیری می‌کند، ولی سهمیه پیامک را مصرف می‌کند.

### سناریو B — مشتری بازگشتی

1. `POST /auth/otp/request/` با همان شماره.
2. `POST /auth/otp/verify/` با کد جدید.
3. `get_or_create` رکورد موجود را برمی‌گرداند؛ حساب تکراری ساخته نمی‌شود.
4. `GET /auth/me/` پروفایل و `GET /auth/addresses/` آدرس‌های ذخیره‌شده را برمی‌گرداند.
5. `GET /orders/` سفارش‌های قبلی را برمی‌گرداند (به‌ترتیب نزولی تاریخ ایجاد).

نکات:

- `last_login` در ورود OTP به‌روزرسانی نمی‌شود (فقط ورود کارکنان با رمز آن را ثبت می‌کند).
- توکن‌های قبلی باطل نمی‌شوند؛ ورود جدید توکن تازه می‌دهد و توکن‌های قدیمی تا انقضا معتبر می‌مانند.
- آدرس پیش‌فرض در فهرست آدرس‌ها اول نمایش داده می‌شود.

### سناریو C — ورود اجباری در زمان Checkout

#### واقعیت معماری

سبد خرید **روی سرور وجود ندارد**. هیچ endpointای برای افزودن/حذف آیتم سبد نیست. سبد در `localStorage` مرورگر نگه داشته می‌شود و فقط در لحظه ثبت سفارش به سرور فرستاده می‌شود.

#### مسیر کاربر مهمان

1. مهمان محصولات را می‌بیند و آیتم‌ها را در `localStorage` ذخیره می‌کند.
2. دکمه «ثبت سفارش» را می‌زند؛ فرانت‌اند ابتدا باید وجود توکن را بررسی کند.
3. اگر مهمان مستقیماً `POST /orders/` بزند:

```json
{
  "success": false,
  "error": {
    "code": "NOT_AUTHENTICATED",
    "message": "درخواست نامعتبر است.",
    "details": { "detail": "Authentication credentials were not provided." }
  }
}
```

وضعیت: `401`.

4. فرانت‌اند شماره موبایل را می‌گیرد و سناریو A/B را اجرا می‌کند.
5. پس از دریافت JWT، همان سبد `localStorage` دوباره به `POST /orders/` فرستاده می‌شود.
6. سفارش به `request.user` (همان مشتری) متصل می‌شود و از این پس در `GET /orders/` او دیده می‌شود.

#### نکات مهم

- اعتبارسنجی کد تخفیف (`POST /orders/validate-promo/`) هم احراز هویت لازم دارد، چون سقف استفاده «به‌ازای هر مشتری» بررسی می‌شود.
- اگر کاربر قبل از ورود کد تخفیف را وارد کرده باشد، باید بعد از ورود دوباره آن را اعتبارسنجی کند.
- آدرسی که در Checkout انتخاب می‌شود باید متعلق به همان حساب باشد؛ در غیر این صورت `404 ADDRESS_NOT_FOUND`.
- اگر توکن در میانه کار منقضی شود، `POST /orders/` پاسخ `401` می‌دهد؛ فرانت باید refresh را اجرا و درخواست را **یک‌بار** تکرار کند.
- سبد در سرور رزرو نمی‌شود؛ بین دیدن منو و ثبت سفارش ممکن است محصول ناموجود شود. در این حالت ثبت سفارش با `422` رد می‌شود و تراکنش کاملاً برمی‌گردد.

### سناریو D — نگه‌داشتن نشست، Refresh و خروج

#### استفاده روزمره

```
GET /api/v1/storefront/orders/
Authorization: Bearer <access_token>
```

- `access` پیش‌فرض ۶۰ دقیقه اعتبار دارد (با `JWT_ACCESS_LIFETIME_MINUTES` تغییرپذیر).
- `refresh` پیش‌فرض ۷ روز اعتبار دارد (با `JWT_REFRESH_LIFETIME_DAYS` تغییرپذیر).
- پاسخ موفق پوشش ندارد.

#### انقضای access

درخواست با توکن منقضی:

```json
{
  "success": false,
  "error": {
    "code": "TOKEN_NOT_VALID",
    "message": "درخواست نامعتبر است.",
    "details": { "detail": "Given token not valid for any token type", "code": "token_not_valid", ... }
  }
}
```

وضعیت: `401`.

فرانت باید:

1. `POST /auth/token/refresh/` با `{ "refresh": "..." }`
2. دریافت `{ "access": "...", "refresh": "..." }`
3. ذخیره هر دو و تکرار درخواست اصلی.

#### چرخش توکن (Rotation)

تنظیمات فعال:

- `ROTATE_REFRESH_TOKENS = True`
- `BLACKLIST_AFTER_ROTATION = True`

یعنی هر بار refresh:

- یک `access` جدید و یک `refresh` جدید صادر می‌شود.
- `refresh` قدیمی **بلک‌لیست** می‌شود و دیگر قابل استفاده نیست.

پیامدها:

| اتفاق | نتیجه |
| --- | --- |
| استفاده دوباره از refresh قدیمی | `401 TOKEN_NOT_VALID` |
| دو تب هم‌زمان با یک refresh، هر دو refresh بزنند | یکی موفق، دیگری `401`؛ فرانت باید توکن مشترک را همگام کند (قفل/قیمت واحد) |
| refresh باطل‌شده یا دستکاری‌شده | `401` |
| refresh منقضی | `401` |

#### خروج

```
POST /api/v1/storefront/auth/token/logout/
Content-Type: application/json

{ "refresh": "..." }
```

- پاسخ: `204` بدون بدنه.
- این endpoint **عمومی** است و احراز هویت نمی‌خواهد.
- فقط `refresh` بلک‌لیست می‌شود.
- اگر توکن از قبل باطل/منقضی باشد، باز هم `204` برمی‌گردد (خطا افشا نمی‌شود).
- **`access` فعلی تا زمان انقضا معتبر می‌ماند** (تا ۶۰ دقیقه). برای خروج مؤثر، کلاینت باید هر دو توکن را پاک کند.
- چون Session وجود ندارد، کوکی‌ای برای پاک‌کردن نیست.

#### جدول تفاوت با Session

| ویژگی | Storefront |
| --- | --- |
| کوکی ورود | ندارد |
| CSRF | لازم نیست |
| خروج سمت سرور | فقط refresh؛ access تا انقضا زنده است |
| ورود چنددستگاهی | مجاز؛ هر ورود توکن مستقل می‌دهد |

### سناریو E — شکست‌ها و ردهای امنیتی

#### E.1 عبور از محدودیت نرخ

- درخواست ششم OTP در یک ساعت برای همان «شماره + IP» → `429`.
- تأیید یازدهم در یک ساعت برای همان «شماره + IP» → `429`، حتی اگر کد درست باشد.
- چون شمارش قبل از view است، تلاش‌های اشتباه هم سهمیه مصرف می‌کنند.
- چند IP یا تغییر ظاهر شماره (`+98` در برابر `09`) می‌تواند سهمیه را دور بزند؛ این محدودیت دفاع لایه‌ای است، نه کنترل قطعی.
- پاسخ `429` شامل `Retry-After` است.

#### E.2 کد منقضی یا نادرست

| وضعیت | پاسخ | آیا کد باقی می‌ماند؟ |
| --- | --- | --- |
| کد وجود ندارد / TTL تمام شده | `400 OTP_EXPIRED` | — |
| کد اشتباه | `400 OTP_INVALID` | بله، تا پایان TTL |
| کد درست | ادامه ورود | خیر، فوراً حذف |
| کد درست اما حساب مسدود | `403 ACCOUNT_BLOCKED` | خیر، کد مصرف شده |
| کد درست اما حساب غیرفعال | `403 ACCOUNT_INACTIVE` | خیر، کد مصرف شده |

هیچ شمارنده تلاش «روی یک کد» وجود ندارد؛ محدودیت اصلی همان throttle ساعتی است.

#### E.3 حساب مسدود یا غیرفعال

دو نقطه کنترل:

1. **هنگام ورود** (`verify_otp`): بعد از تأیید کد، `ACCOUNT_BLOCKED` یا `ACCOUNT_INACTIVE` (هر دو `403`).
2. **روی هر درخواست محافظت‌شده** (`IsActiveCustomer`): اگر توکن معتبر باشد ولی کاربر مسدود/غیرفعال شده باشد، پاسخ `403` است و هیچ داده‌ای برنمی‌گردد.

پیامد مهم: مسدودکردن یک مشتری، توکن‌های صادرشده قبلی را باطل نمی‌کند، ولی آن‌ها دیگر به هیچ منبع محافظت‌شده‌ای دسترسی ندارند. endpointهای عمومی (منو، جست‌وجو، وضعیت رستوران) همچنان برای او کار می‌کنند.

#### E.4 استفاده از JWT مشتری در Backoffice

`BackofficeAPIView` فقط `SessionAuthentication` را می‌پذیرد. بنابراین:

```
GET /api/v1/backoffice/orders/
Authorization: Bearer <customer_access_token>
```

پاسخ `403` است (بدون سشن، کاربر ناشناس است و `IsStaffUser` رد می‌کند). حتی اگر همان مشتری `is_staff=True` باشد، هدر Bearer نادیده گرفته می‌شود و باید با `POST /backoffice/auth/login/` سشن بگیرد.

#### E.5 جمع‌بندی خطاهای احراز هویت

| وضعیت | کد | معنا |
| --- | --- | --- |
| `400` | `OTP_INVALID` | کد نادرست |
| `400` | `OTP_EXPIRED` | کد منقضی/مصرف‌شده/درخواست‌نشده |
| `401` | `NOT_AUTHENTICATED` | توکن ارسال نشده |
| `401` | `TOKEN_NOT_VALID` | توکن منقضی/باطل/نامعتبر |
| `403` | `ACCOUNT_BLOCKED` | حساب مسدود |
| `403` | `ACCOUNT_INACTIVE` | حساب غیرفعال |
| `403` | `PERMISSION_DENIED` | رد شدن `IsActiveCustomer` روی درخواست‌های بعدی |
| `429` | `THROTTLED` | عبور از سهمیه |
| `422` | `VALIDATION_ERROR` | شماره موبایل نامعتبر |

### سناریو ۱ — کشف منو، جست‌وجوی هوشمند و گردونه شانس

#### ۱.۱ وضعیت رستوران

```
GET /api/v1/storefront/cms/restaurant-status/
```

```json
{
  "is_open": true,
  "is_temporarily_closed": false,
  "open_time": "11:00",
  "close_time": "01:00",
  "in_zone_delivery_fee": 50000,
  "out_zone_delivery_fee": 100000,
  "min_delivery_order_amount": 150000,
  "packaging_fee": 15000,
  "prep_time_buffer_minutes": 5
}
```

قواعد `is_open`:

- اگر `is_temporarily_closed=True` باشد، همیشه بسته است (صرف‌نظر از ساعت).
- اگر ساعت باز و بسته **مساوی** باشند، بسته در نظر گرفته می‌شود (حالت مبهم).
- اگر `open_time < close_time` باشد، بازه همان‌روز است (مثلاً ۰۹:۰۰ تا ۲۲:۰۰).
- اگر `open_time > close_time` باشد، بازه شبانه است (مثلاً ۱۱:۰۰ تا ۰۱:۰۰): از ساعت باز تا نیمه‌شب **یا** از نیمه‌شب تا ساعت بسته.
- محاسبه با ساعت محلی سرور (Asia/Tehran) انجام می‌شود.

نکته: بسته بودن رستوران، **دیدن منو را مسدود نمی‌کند**؛ فقط `POST /orders/` و شروع/تلاش مجدد پرداخت را رد می‌کند.

#### ۱.۲ دیدن منو

```
GET /api/v1/storefront/catalog/menu/
```

```json
{
  "categories": [

      "id": 1,
```

قواعد دقیق:

| --- | --- |
| دسته‌بندی غیرفعال | نمایش داده نمی‌شود |
| دسته‌بندی حذف‌شده (soft delete) | نمایش داده نمی‌شود |
| محصول `AVAILABLE` | نمایش داده می‌شود |

| ترتیب دسته‌ها | `display_order` سپس `id` |
| ترتیب محصولات | `display_order` سپس `name` |
| کش | ۱ ساعت؛ هر نوشتن کاتالوگ آن را پاک می‌کند |

> تفاوت مهم: پاسخ منو `compare_at_price` و درصد تخفیف را ندارد. برای نمایش نشان تخفیف باید از `GET /catalog/products/` یا `GET /catalog/products/<slug>/` استفاده کرد.

#### ۱.۳ جزئیات محصول

```
GET /api/v1/storefront/catalog/products/<slug>/
```

- محصول `HIDDEN` → `404 PRODUCT_NOT_FOUND`.
- محصول `OUT_OF_STOCK` **برمی‌گردد** (تا فرانت بتواند قیمت/توضیحات را با دکمه غیرفعال نشان دهد).
- فقط افزودنی‌های `is_available=True` و حذف‌نشده در `addons` می‌آیند.
- هر افزودنی شامل `addon_id`, `name`, `price`, `min_quantity`, `max_quantity` است.

#### ۱.۴ جست‌وجو و فیلتر

```
GET /api/v1/storefront/catalog/products/?q=پیتزا&category=pizza&available=true&sort=price_asc&limit=20&offset=0
```

| پارامتر | اعتبارسنجی | رفتار |
| --- | --- | --- |
| `q` | حداکثر ۱۰۰ کاراکتر | بیشتر از ۱۰۰ → `400 INVALID` |
| `category` | slug | ناموجود/غیرفعال → `404 CATEGORY_NOT_FOUND` |
| `category_id` | عدد ≥ ۱ | ناموجود/غیرفعال → `404 CATEGORY_NOT_FOUND` |
| `min_price` | ۰ تا ۱٬۰۰۰٬۰۰۰٬۰۰۰ | شامل خود مقدار |
| `max_price` | ۰ تا ۱٬۰۰۰٬۰۰۰٬۰۰۰ | اگر `min > max` → `400` |
| `available` | boolean | `true` فقط `AVAILABLE`؛ `false` فقط `OUT_OF_STOCK`؛ حذف → هر دو |
| `discount` | boolean | `true` فقط `compare_at_price > price`؛ `false` فقط بدون تخفیف |
| `is_main_dish` | boolean | فیلتر روی پرچم غذای اصلی |
| `sort` | `relevance`, `popularity`, `default`, `newest`, `oldest`, `price_asc`, `price_desc` | مقدار نامعتبر → `400` |
| `limit` | پیش‌فرض ۲۰ | حداکثر ۱۰۰ (مقادیر بیشتر به ۱۰۰ محدود می‌شوند) |
| `offset` | ≥ ۰ | صفحه‌بندی Limit/Offset |

قواعد پنهان‌سازی:

- محصول `HIDDEN` هرگز برنمی‌گردد، حتی اگر slug یا دسته‌اش صریحاً داده شود.
- محصول دسته غیرفعال یا حذف‌شده هرگز برنمی‌گردد.
- اگر هم `category` و هم `category_id` داده شود، باید به **یک** دسته اشاره کنند؛ در غیر این صورت `404`.
- دسته‌بندی‌ها تخت‌اند؛ فیلتر دسته فقط همان دسته را می‌گیرد.

پاسخ:

```json
{
  "count": 3,
  "next": "http://host/api/v1/storefront/catalog/products/?...&offset=20",
  "previous": null,
  "results": [ { "id": 10, "name": "...", "price": 180000, "compare_at_price": 220000, "discount_percent": 18, "is_discounted": true, "status": "AVAILABLE", "category": { "...": "..." } } ]
}
```

##### موتور جست‌وجو (رفتار واقعی)

1. **نرمال‌سازی query** روی ورودی کاربر (داده‌های ذخیره‌شده دست‌نخورده می‌مانند):
   - `ي` عربی → `ی` فارسی، `ك` عربی → `ک` فارسی.
   - ارقام عربی/فارسی → ارقام لاتین.
   - حذف نیم‌فاصله (ZWNJ)، joiner، علامت‌های جهت و کشیده.
   - جمع‌کردن فاصله‌ها، trim و برش تا ۱۰۰ کاراکتر.
   - حداکثر ۸ توکن برای جست‌وجو.
2. **Full-Text جست‌وجوی PostgreSQL** با پیکربندی `simple`:
   - نام محصول وزن A، نام دسته وزن B، توضیحات وزن C.
   - کلمات query با AND ترکیب می‌شوند؛ با این حال تطبیق زیررشته‌ای کل عبارت (`icontains`) یا شباهت Trigram به‌تنهایی هم برای برگشت نتیجه کافی است.
   - هر کلمه می‌تواند به هر یک از شکل‌های فارسی/عربی خودش یا مترادف‌هایش تطبیق پیدا کند (OR داخل یک کلمه).
3. **Trigram** روی نام محصول با آستانه پیش‌فرض `0.2` برای غلط املایی و تطبیق جزئی.
4. **زیررشته** `name__icontains` نیز پذیرفته می‌شود.
5. مرتب‌سازی پیش‌فرض وقتی `q` هست و `sort` داده نشده: امتیاز ترکیبی FTS + شباهت Trigram، سپس `display_order`، `name`، `id`.
6. `sort=popularity` بر اساس مجموع تعداد آیتم‌های سفارش‌های **پرداخت‌شده** (وضعیت‌های PROCESSING/READY/COMPLETED) محاسبه می‌شود.

مترادف‌های فعال (دوطرفه):

| گروه |
| --- |
| برگر، همبرگر |
| مرغ، چیکن، جوجه |
| نوشابه، نوشیدنی، کوکاکولا، کوکا، پپسی |
| سیب‌زمینی، فرای، فریز |
| سوسیس، هات‌داگ |
| پنیر، چیز |
| قارچ، ماشروم |
| میگو، shrimp |

مثال‌ها:

- جست‌وجوی «پيتزا» (با ي عربی) محصول «پیتزا» را پیدا می‌کند.
- جست‌وجوی «همبرگر» محصولات «برگر» را هم پیدا می‌کند.
- جست‌وجوی «چیز» افزودنی/محصول «پنیر» را هم پیدا می‌کند.
- جست‌وجوی «پیتزا پنیر» فقط محصولاتی را می‌آورد که **هر دو** کلمه در نام/دسته/توضیحاتشان باشد.

##### «شاید منظورتان این بود»

اگر query داده شده باشد و **هیچ نتیجه‌ای** برنگردد:

- نزدیک‌ترین نام محصول یا دسته با شباهت Trigram ≥ آستانه `0.25` محاسبه می‌شود.
- اگر پیدا شود، فیلد `did_you_mean` به پاسخ اضافه می‌شود؛ در غیر این صورت اصلاً اضافه نمی‌شود.
- برای queryهای کمتر از ۲ کاراکتر، این قابلیت اجرا نمی‌شود.

### سناریو ۲ — شخصی‌سازی آیتم‌ها، Cart Upsell و کد تخفیف

#### ۲.۱ انتخاب محصول و افزودنی

کاربر محصول را از منو/جست‌وجو انتخاب می‌کند، جزئیات را می‌بیند و افزودنی‌ها را انتخاب می‌کند. محدودیت‌ها در `POST /orders/` اعمال می‌شوند:

| قاعده | نتیجه تخلف |
| --- | --- |
| محصول باید وجود داشته باشد | `422` با `details.missing_product_ids` |
| محصول نباید `HIDDEN` باشد | `422` |
| محصول باید `AVAILABLE` باشد | `422` با `details.status` |
| دسته محصول باید فعال باشد | `422` |
| افزودنی باید برای همان محصول تعریف شده باشد | `422` با `addon_id` |
| افزودنی باید `is_available=True` باشد | `422` |
| `0 ≤ quantity ≤ max_quantity` | `422` با `min_quantity`, `max_quantity`, `provided` |
| تعداد محصول ≥ ۱ | `400` (اعتبارسنجی serializer) |
| تعداد افزودنی ≥ ۰ | `400` (اعتبارسنجی serializer) |

نکات دقیق:

- `min_quantity` در پاسخ محصول نمایش داده می‌شود ولی در ثبت سفارش **اجباری نیست**؛ فقط سقف `max_quantity` اعمال می‌شود.
- تعداد افزودنی به‌ازای **هر خط سفارش** است، نه ضربدر تعداد محصول. مثال: ۲ عدد برگر + ۱ پنیر = قیمت ۲ برگر + قیمت ۱ پنیر.
- افزودنی با تعداد `0` پذیرفته و نادیده گرفته می‌شود (ردیفی ساخته نمی‌شود).
- افزودنی که مدیر آن را از دسترس خارج کرده، در جزئیات محصول هم نمایش داده نمی‌شود؛ اگر کلاینت از داده قدیمی استفاده کند، ثبت سفارش `422` می‌دهد.
- ارسال دو خط با یک `product_id` مجاز است و دو ردیف جدا می‌سازد.

#### ۲.۲ Upsell سبد

فرانت بعد از هر تغییر سبد می‌تواند `GET /catalog/upsell/` را صدا بزند و محصولات مکمل (نوشیدنی/سیب‌زمینی) را پیشنهاد دهد. این فهرست مستقل از محتوای سبد است و در سرور محاسبه/ذخیره نمی‌شود.

#### ۲.۳ اعتبارسنجی کد تخفیف

```
POST /api/v1/storefront/orders/validate-promo/
Authorization: Bearer <access>
Content-Type: application/json

{ "code": "welcome20", "subtotal": 400000 }
```

پاسخ موفق:

```json
{
  "code": "WELCOME20",
  "discount_type": "PERCENTAGE",
  "discount_value": 20,
  "discount_amount": 80000,
  "subtotal": 400000,
  "discounted_subtotal": 320000
}
```

قواعد:

- کد با `trim` و `upper` نرمال می‌شود (نامساوی حروف مهم نیست).
- کد خالی/`null` در ثبت سفارش یعنی «بدون تخفیف»؛ در endpoint اعتبارسنجی، `code` اجباری است.
- `subtotal` همان جمع خطوط محصولات (با افزودنی‌ها) و **قبل از** هزینه ارسال/بسته‌بندی و تخفیف است.
- تخفیف درصدی: `subtotal × value // 100`، سپس محدود به `max_discount_amount` (اگر تعریف شده باشد).
- تخفیف ثابت: مبلغ ثابت.
- در هر دو حالت تخفیف از `subtotal` بیشتر نمی‌شود و منفی نیست.
- فقط **یک** کد تخفیف در هر سفارش قابل استفاده است.

##### خطاهای ممکن

| شرط | کد | وضعیت |
| --- | --- | --- |
| کد وجود ندارد | `PROMO_CODE_NOT_FOUND` | `422` |
| `is_active=False` | `PROMO_CODE_INACTIVE` | `422` |
| زمان فعلی قبل از `valid_from` | `PROMO_CODE_NOT_STARTED` | `422` |
| زمان فعلی بعد از `valid_until` | `PROMO_CODE_EXPIRED` | `422` |
| `subtotal < min_order_amount` | `PROMO_CODE_MIN_ORDER` | `422` |
| سقف کل استفاده پر شده | `PROMO_CODE_TOTAL_LIMIT` | `422` |
| سقف استفاده همین مشتری پر شده | `PROMO_CODE_CUSTOMER_LIMIT` | `422` |
| کد مخصوص سفارش اول است و مشتری قبلاً سفارش پرداخت‌شده دارد | `PROMO_CODE_FIRST_ORDER_ONLY` | `422` |

##### نکات ظریف سهمیه

- «سفارش اول» بر اساس وجود **هر** سفارش با `paid_at` تعیین می‌شود؛ حتی اگر بعداً لغو یا بازپرداخت شده باشد.
- استفاده‌ها از جدول `PromoCodeUsage` شمرده می‌شوند؛ ردیف‌های soft-delete شده شمرده نمی‌شوند.
- هنگام **ثبت سفارش**، ردیف استفاده بلافاصله ساخته می‌شود. یعنی سهمیه کد **رزرو** می‌شود، حتی قبل از پرداخت.
- اگر سفارش در وضعیت `UNPAID` لغو شود (توسط مدیر یا به‌صورت خودکار بعد از ۱۵ دقیقه)، ردیف استفاده حذف/soft-delete می‌شود و سهمیه آزاد می‌گردد.
- اگر سفارش **پرداخت‌شده** لغو شود، سهمیه آزاد نمی‌شود (تخفیف واقعاً استفاده شده است).
- `validate-promo` هیچ رزروی انجام نمی‌دهد؛ فقط محاسبه و بررسی است. بین اعتبارسنجی و ثبت سفارش ممکن است سهمیه پر شود.
- کد تخفیف در زمان **پرداخت مجدد** دوباره اعتبارسنجی نمی‌شود؛ مبلغ تخفیف در سفارش snapshot شده است.

#### ۲.۴ حالت‌های مرزی سناریو ۲

| سناریو | رفتار |
| --- | --- |
| کد با فاصله ابتدا/انتها | پذیرفته می‌شود |
| کد با حروف کوچک | پذیرفته می‌شود (`welcome20` = `WELCOME20`) |
| کد منقضی دقیقاً در لحظه `valid_until` | پذیرفته می‌شود؛ فقط `now > valid_until` رد می‌شود |
| کد قبل از `valid_from` | رد می‌شود |
| تخفیف درصدی ۱۰۰٪ | `discounted_subtotal = 0` |
| تخفیف ثابت بزرگ‌تر از سبد | تخفیف = `subtotal` (نه بیشتر) |
| افزودنی ناموجود | `422`؛ سفارش ثبت نمی‌شود |
| سبد خالی | `400` (serializer) |
| کد معتبر ولی سبد زیر حداقل ارسال | `validate-promo` موفق است؛ ثبت سفارش `DELIVERY` با `422 MIN_DELIVERY_ORDER_AMOUNT` رد می‌شود |
| استفاده از کد روی سفارش `PICKUP` | حداقل مبلغ ارسال بررسی نمی‌شود؛ تخفیف اعمال می‌شود |

### سناریو ۳ — ارسال در مقابل تحویل حضوری و قواعد آدرس

#### ۳.۱ مدیریت آدرس

| متد و مسیر | کار |
| --- | --- |
| `GET /auth/addresses/` | فهرست آدرس‌های زنده؛ پیش‌فرض اول، سپس جدیدترین |
| `POST /auth/addresses/` | ساخت آدرس جدید یا جایگزینی یکی از آدرس‌های موجود |
| `GET /auth/addresses/<id>/` | مشاهده یک آدرس (فقط مال خود کاربر) |
| `PATCH /auth/addresses/<id>/` | ویرایش جزئی |
| `DELETE /auth/addresses/<id>/` | حذف نرم (`204`) |
| `POST /auth/addresses/<id>/set-default/` | انتخاب به‌عنوان پیش‌فرض |

بدنه ساخت آدرس:

```json
{
  "title": "خانه",
  "address_text": "تهران، خیابان ...، پلاک ۱۲، واحد ۳",
  "recipient_name": "علی",
  "recipient_phone": "09121234567",
  "is_out_of_zone": false,
  "replace_address_id": null
}
```

قواعد دقیق:

1. **حداکثر ۴ آدرس زنده** برای هر مشتری. آدرس‌های حذف‌شده شمرده نمی‌شوند.
2. آدرس جدید **همیشه** `is_default=True` می‌شود و پیش‌فرض قبلی خودکار `False` می‌شود.
3. `is_default` ارسالی کلاینت در ساخت نادیده گرفته می‌شود.
4. اگر مشتری ۴ آدرس دارد و آدرس پنجم بفرستد:
   `422` با کد `ADDRESS_LIMIT_REACHED` و پیام راهنما.
5. راه‌حل بدون خطا: ارسال `replace_address_id` برابر با شناسه یکی از آدرس‌های خودش. آن آدرس **در همان رکورد** با داده جدید به‌روزرسانی می‌شود (تعداد ثابت می‌ماند) و پیش‌فرض می‌شود.
6. `replace_address_id` متعلق به کاربر دیگر یا ناموجود → `404 ADDRESS_NOT_FOUND`.
7. `address_text` خالی یا فقط فاصله → `400` (اعتبارسنجی serializer).
8. برای ویرایش، `PATCH` با `is_default=true` آدرس را پیش‌فرض می‌کند و بقیه پیش‌فرض‌ها را برمی‌دارد.
9. `PATCH` با `is_default=false` روی آدرس پیش‌فرض فعلی، آن را از پیش‌فرض بودن خارج می‌کند؛ در این حالت ممکن است مشتری **هیچ آدرس پیش‌فرضی** نداشته باشد.
10. حذف آدرس پیش‌فرض، آدرس دیگری را خودکار پیش‌فرض نمی‌کند.
11. آدرس کاربر دیگر با `GET/PATCH/DELETE` → `404 ADDRESS_NOT_FOUND` (نه `403`؛ وجود آدرس افشا نمی‌شود).
12. `is_out_of_zone` را خود مشتری تعیین می‌کند؛ سیستم موقعیت‌سنجی یا geofencing ندارد.

#### ۳.۲ انتخاب نوع تحویل

```json
{ "delivery_type": "PICKUP" }
```

```json
{ "delivery_type": "DELIVERY", "address_id": 7 }
```

| نوع | آدرس | هزینه ارسال | هزینه بسته‌بندی | حداقل مبلغ |
| --- | --- | --- | --- | --- |
| `PICKUP` | اختیاری (اگر داده شود فقط اعتبارسنجی مالکیت می‌شود) | `0` | همیشه اضافه می‌شود | ندارد |
| `DELIVERY` | **اجباری** | `in_zone` یا `out_zone` بر اساس `is_out_of_zone` | همیشه اضافه می‌شود | `subtotal` باید ≥ `min_delivery_order_amount` باشد |

نکات:

- در `DELIVERY` آدرس انتخاب‌شده در همان تراکنش **پیش‌فرض** مشتری می‌شود.
- در `PICKUP` آدرس پیش‌فرض تغییر نمی‌کند، حتی اگر `address_id` ارسال شود.
- `min_delivery_order_amount` روی `subtotal` **قبل از تخفیف** بررسی می‌شود؛ کد تخفیف به رسیدن به حداقل کمک نمی‌کند.
- مبلغ نهایی: `max(0, subtotal − discount) + delivery_fee + packaging_fee`.
- اگر آدرس حذف‌شده باشد → `404 ADDRESS_NOT_FOUND`.
- اگر `DELIVERY` بدون آدرس باشد → `422` با `details.address_id`.
- اگر آدرس متعلق به کاربر دیگر باشد → `404 ADDRESS_NOT_FOUND`.

#### ۳.۳ حفظ سابقه آدرس

هنگام ثبت سفارش، متن آدرس، نام گیرنده و شماره گیرنده در سفارش **snapshot** می‌شوند. بنابراین:

- ویرایش یا حذف آدرس بعدی، فاکتور و تاریخچه سفارش را تغییر نمی‌دهد.
- حتی با `SET_NULL` شدن FK آدرس پس از حذف، متن snapshot باقی می‌ماند.

#### ۳.۴ حالت‌های مرزی سناریو ۳

| سناریو | رفتار |
| --- | --- |
| ساخت آدرس پنجم | `422 ADDRESS_LIMIT_REACHED` |
| ساخت آدرس با `replace_address_id` معتبر | موفق؛ تعداد ۴ می‌ماند؛ آدرس جایگزین پیش‌فرض می‌شود |
| جایگزینی آدرس کاربر دیگر | `404` |
| حذف آدرس پیش‌فرض | حذف نرم؛ هیچ آدرس دیگری پیش‌فرض نمی‌شود |
| سپس ساخت آدرس جدید | آدرس جدید پیش‌فرض می‌شود |
| Checkout با آدرس غیرپیش‌فرض | آن آدرس پیش‌فرض می‌شود (فقط `DELIVERY`) |
| آدرس با `is_out_of_zone=true` | هزینه ارسال برون‌منطقه اعمال می‌شود |
| `PICKUP` با سبد کوچک | مجاز؛ حداقل مبلغ ارسال ندارد |
| `DELIVERY` با سبد زیر حداقل | `422 MIN_DELIVERY_ORDER_AMOUNT` با `min_delivery_order_amount` و `subtotal` |

#### ۴.۱ ثبت سفارش

```
POST /api/v1/storefront/orders/
Authorization: Bearer <access>
Content-Type: application/json

{
  "delivery_type": "DELIVERY",
```

ترتیب اعتبارسنجی در سرور:

1. رستوران باز است؟ (`409 RESTAURANT_CLOSED`)
2. `delivery_type` معتبر است؟ (`422`)
3. آدرس مالکیت/وجود دارد؟ (`404 ADDRESS_NOT_FOUND`)
4. `DELIVERY` بدون آدرس؟ (`422`)
5. قفل ردیف کد تخفیف (برای جلوگیری از مصرف هم‌زمان آخرین سهمیه).
6. محاسبه زمان آماده‌سازی: `max(prep_time محصولات) + prep_time_buffer_minutes` (حداقل بافر).
7. ساخت ردیف سفارش با `PENDING_PAYMENT` / `UNPAID` و `expires_at = now + 15 دقیقه`.
8. اعتبارسنجی محصولات و افزودنی‌ها و ساخت ردیف‌ها (`422`).
9. بررسی حداقل مبلغ ارسال (`422 MIN_DELIVERY_ORDER_AMOUNT`).
10. بررسی شرایط کد تخفیف و ثبت `PromoCodeUsage` (`422` با کدهای PROMO_*).
11. محاسبه و ذخیره `subtotal`, `discount_amount`, `total_amount`.

کل این فرآیند در یک تراکنش اتمیک است؛ اگر هر مرحله شکست بخورد، **هیچ سفارش، آیتم یا استفاده از کد تخفیف ثبت نمی‌شود**.

نکات:

- `expected_ready_at` تا قبل از پرداخت `null` است.
- `daily_number` تا قبل از پرداخت `null` است.
- هیچ رزرو موجودی یا قفل محصولی وجود ندارد؛ فقط وضعیت `status` بررسی می‌شود.
- `notes_to_kitchen` اختیاری و آزاد است.

#### ۴.۲ شروع پرداخت

```
POST /api/v1/storefront/payments/request/
Authorization: Bearer <access>

{ "order_id": 501 }
```

پاسخ `201`:

```json
{
  "payment_url": "https://sandbox.zarinpal.com/pg/StartPay/S...",
  "authority": "S...",
  "amount": 369000
}
```

پیش‌شرط‌ها و خطاها:

| شرط | نتیجه |
| --- | --- |
| سفارش مال کاربر نیست/وجود ندارد | `404 ORDER_NOT_FOUND` |
| وضعیت سفارش `PENDING_PAYMENT` نیست | `409 INVALID_ORDER_STATE` |
| `payment_status` قبلاً `PAID` است | `409 INVALID_ORDER_STATE` |
| `expires_at` گذشته است | `409 INVALID_ORDER_STATE` |
| رستوران بسته است | `422` (`RestaurantClosedError` از مسیر بازاعتبارسنجی) |
| محصولی دیگر `AVAILABLE` نیست | `422` با `product_id` |
| افزودنی‌ای دیگر موجود نیست | `422` با `addon_id` |
| خطای درگاه/نبود Merchant ID | `402 ZARINPAL_REQUEST_FAILED` |

سپس فرانت کاربر را به `payment_url` می‌فرستد. مبلغ همیشه از `order.total_amount` سرور خوانده می‌شود، نه از کلاینت.

#### ۴.۳ بازگشت از درگاه (Callback)

```
GET /api/v1/storefront/payments/callback/?Authority=S...&Status=OK
```

این endpoint عمومی است (کاربر ممکن است توکن نداشته باشد).

رفتار:

1. پرداخت با `authority` پیدا می‌شود؛ اگر نباشد → استثنا و در نهایت redirect به صفحه شکست.
2. اگر قبلاً `SUCCEEDED` باشد → همان پرداخت برگردانده می‌شود (idempotent؛ تأیید دوباره انجام نمی‌شود).
3. اگر `FAILED` یا `CANCELED` باشد → خطای «قابل تأیید نیست» و redirect شکست.
4. اگر `Status != "OK"` باشد → پرداخت `FAILED` می‌شود (بدون تماس با زرین‌پال) و redirect شکست.
5. اگر `Status=OK` باشد → زرین‌پال verify می‌شود:
   - کد `100` = موفق تازه.
   - کد `101` = قبلاً تأیید شده؛ **موفق** در نظر گرفته می‌شود.
   - هر کد دیگر → پرداخت `FAILED` و خطا.
6. در موفقیت:
   - `Payment.status = SUCCEEDED` و `ref_id` ذخیره می‌شود.
   - سفارش `PAID` + `PROCESSING` می‌شود.
   - `paid_at` ثبت و `expected_ready_at = paid_at + prep_time_minutes` محاسبه می‌شود.
   - `daily_number` روزانه اختصاص می‌یابد.
   - پیامک «سفارش جدید» به مدیر (در صورت تنظیم `MANAGER_PHONE`) و رویداد SSE منتشر می‌شود.
7. پاسخ مرورگر: `302` به `PAYMENT_FRONTEND_RESULT_URL` با یکی از این دو:
   - `?status=success&authority=S...`
   - `?status=failed&authority=S...`

نکات:

- پارامترها **حساس به حروف** هستند: `Authority` و `Status`.
- اگر `?format=json` اضافه شود و پرداخت موفق باشد، به‌جای redirect، JSON پرداخت برمی‌گردد. در حالت شکست، این پارامتر مانع redirect نمی‌شود.
- اگر `PAYMENT_FRONTEND_RESULT_URL` تنظیم نشده باشد: موفقیت JSON و شکست پاسخ `402` می‌دهد.
- تأیید در یک تراکنش اتمیک با تغییر وضعیت سفارش انجام می‌شود؛ اگر تغییر سفارش شکست بخورد، رکورد پرداخت هم rollback می‌شود.

#### ۴.۴ مشاهده وضعیت پرداخت

```
GET /api/v1/storefront/payments/status/<authority>/
Authorization: Bearer <access>
```

- فقط پرداخت سفارش خود کاربر.
- پرداخت متعلق به کاربر دیگر → `403` («این تراکنش متعلق به شما نیست.»).
- Authority ناموجود در کد به خطای ۴۰۴ نگاشت نشده و به خطای داخلی سرور می‌رسد؛ فرانت باید این حالت را به‌عنوان «تراکنش نامعتبر» نمایش دهد.

#### ۴.۵ شکست پرداخت و تلاش مجدد

اگر کاربر در درگاه انصراف بدهد یا پرداخت ناموفق باشد:

- سفارش همچنان `PENDING_PAYMENT` / `UNPAID` می‌ماند (تا پایان پنجره ۱۵ دقیقه‌ای).
- `POST /payments/retry/` با همان `{ "order_id": ... }` قابل استفاده است.
- retry دقیقاً همان مسیر `request` را طی می‌کند: بررسی وضعیت، بررسی انقضا، بازاعتبارسنجی رستوران/محصول/افزودنی و ساخت **یک رکورد Payment جدید** با Authority جدید.
- رکوردهای Payment قبلی حذف نمی‌شوند؛ تاریخچه باقی می‌ماند.
- خطاها همان جدول بخش ۴.۲ است.

#### ۴.۶ انصراف خودکار بعد از ۱۵ دقیقه

- یک تسک Celery Beat هر **۶۰ ثانیه** سفارش‌های `PENDING_PAYMENT` با `expires_at < now` را پیدا می‌کند.
- برای هر سفارش: `status = CANCELED`، `canceled_at = now`، `cancellation_reason = "auto: payment timeout"`.
- `payment_status` **تغییر نمی‌کند** و `UNPAID` می‌ماند.
- سهمیه کد تخفیف آزاد می‌شود (ردیف استفاده soft-delete می‌شود).
- رویداد SSE منتشر می‌شود.
- پیامکی به مشتری ارسال نمی‌شود.

پیامدها:

- بعد از انصراف خودکار، `retry` و `request` با `409 INVALID_ORDER_STATE` رد می‌شوند.
- اگر کاربر درست بعد از لغو خودکار از درگاه برگردد، تأیید پرداخت با خطای وضعیت سفارش مواجه می‌شود و به صفحه شکست هدایت می‌شود. اگر زرین‌پال پول را گرفته باشد، رکورد پرداخت در `PENDING` می‌ماند و نیاز به بررسی/بازپرداخت دستی دارد.
- تسک دیگری هر **۵ دقیقه** پرداخت‌های `PENDING` قدیمی‌تر از ۳ دقیقه را دوباره تأیید می‌کند (برای وقتی که callback به هر دلیل نرسیده). این کار به‌خاطر idempotent بودن verify بی‌خطر است.

#### ۴.۷ حالت‌های مرزی سناریو ۴

| سناریو | رفتار |
| --- | --- |
| دو کلیک روی «پرداخت» | دو Authority و دو رکورد Payment ساخته می‌شود؛ هر دو به یک سفارش اشاره می‌کنند |
| پرداخت موفق دو بار روی یک Authority | بار دوم idempotent برمی‌گردد؛ سفارش دوباره PAID نمی‌شود |
| پرداخت با `Status=NOK` | Payment `FAILED`؛ سفارش `PENDING_PAYMENT` می‌ماند |
| callback بدون `Authority` | شکست و redirect |
| callback با Authority جعلی | شکست و redirect |
| پرداخت بعد از ۱۵ دقیقه | `409` در retry/request؛ سفارش تا اجرای Beat ممکن است هنوز `PENDING_PAYMENT` دیده شود ولی پرداخت مسدود است |
| رستوران بین ثبت سفارش و پرداخت بسته شود | `422`؛ پرداخت شروع نمی‌شود |
| محصول بین ثبت و پرداخت ناموجود شود | `422`؛ پرداخت شروع نمی‌شود |
| دو سفارش هم‌زمان با آخرین سهمیه کد تخفیف | قفل ردیف کد در ثبت سفارش از مصرف بیش از سقف جلوگیری می‌کند؛ یکی موفق، دیگری `422` |
| پرداخت هم‌زمان دو Authority از یک سفارش | اولی سفارش را PAID می‌کند؛ دومی به خطای وضعیت می‌خورد و پرداختش در PENDING می‌ماند (تسویه دستی لازم است) |
| تغییر مبلغ سفارش توسط کلاینت | بی‌اثر است؛ مبلغ از سرور خوانده می‌شود |

### سناریو ۵ — پیگیری زنده و اقدامات پس از سفارش

#### ۵.۱ چرخه وضعیت

```
PENDING_PAYMENT ──(پرداخت موفق)──> PROCESSING ──(مدیر)──> READY ──(مدیر)──> COMPLETED
       │
       └──(۱۵ دقیقه بدون پرداخت / لغو مدیر)──> CANCELED
```

| وضعیت | معنا برای مشتری |
| --- | --- |
| `PENDING_PAYMENT` | سفارش ثبت شده، منتظر پرداخت |
| `PROCESSING` | پرداخت شده، در آشپزخانه |
| `READY` | آماده تحویل/ارسال |
| `COMPLETED` | تحویل شده (آرشیو) |
| `CANCELED` | لغو شده |

وضعیت پرداخت:

| `payment_status` | معنا |
| --- | --- |
| `UNPAID` | پرداخت نشده |
| `PAID` | پرداخت شده |
| `AWAITING_REFUND` | لغو شده و منتظر بازگشت وجه دستی |
| `REFUNDED` | بازپرداخت ثبت شده |

#### ۵.۲ زمان آماده‌سازی و شماره روزانه

- `prep_time_minutes = بیشترین prep_time محصولات + بافر تنظیمات` (پیش‌فرض بافر ۵ دقیقه).
- `expected_ready_at` در لحظه پرداخت محاسبه می‌شود: `paid_at + prep_time_minutes`.
- اگر مدیر زمان آماده‌سازی را تغییر دهد (فقط در `PROCESSING`/`READY`)، مقدار از **`paid_at`** بازمحاسبه می‌شود، نه از زمان تغییر؛ بنابراین ETA با هر تغییر به عقب پرت نمی‌شود.
- `daily_number` در لحظه پرداخت و به‌ازای هر روز (بر اساس تاریخ تهران) اختصاص می‌یابد. شمارنده Redis است و در صورت خطا fallback دیتابیس دارد؛ یکتایی با constraint تضمین می‌شود.
- پیامک‌ها:
  - سفارش جدید → مدیر (`MANAGER_PHONE`).
  - آماده شدن سفارش → مشتری.
  - تغییر زمان آماده‌سازی → مشتری.
  - در محیط بدون تنظیمات sms.ir، پیامک فقط در لاگ ثبت می‌شود و وضعیت سفارش تغییری نمی‌کند.

#### ۵.۳ پیگیری زنده با SSE

```
GET /api/v1/storefront/orders/<id>/stream/
Authorization: Bearer <access>
Accept: text/event-stream
```

- فقط سفارش خود کاربر؛ در غیر این صورت `404 ORDER_NOT_FOUND`.
- پاسخ `StreamingHttpResponse` با `Content-Type: text/event-stream`، `Cache-Control: no-cache` و `X-Accel-Buffering: no`.
- هر ۱۵ ثانیه یک فریم کامنت `: ping` برای زنده نگه‌داشتن اتصال فرستاده می‌شود.
- در صورت خطای Redis، یک فریم `: error` و پایان استریم.

قالب رویدادها:

```
event: order.status_changed
data: {"event_type":"order.status_changed","order_id":501,"daily_number":42,"status":"READY","payment_status":"PAID","expected_ready_at":"2026-11-27T10:50:00+03:30","cancellation_requested":false,"timestamp":"2026-11-27T10:45:00+03:30"}
```

انواع رویداد منتشرشده:

| event | چه زمانی |
| --- | --- |
| `order.created_or_paid` | بعد از تأیید موفق پرداخت |
| `order.status_changed` | READY، COMPLETED، لغو مدیر، لغو خودکار |
| `order.prep_time_updated` | تغییر زمان آماده‌سازی توسط مدیر |
| `order.cancellation_requested` | ثبت درخواست لغو توسط مشتری |

نکات مهم برای فرانت:

- استریم **وضعیت فعلی را در ابتدا نمی‌فرستد** و رویدادهای گذشته را بازپخش نمی‌کند. ابتدا `GET /orders/<id>/` را بگیرید، بعد استریم را باز کنید.
- هیچ فیلد `id:` یا `retry:` ارسال نمی‌شود؛ برای اتصال مجدد باید منطق دستی داشت.
- چون `StorefrontAPIView` فقط `JWTAuthentication` دارد و `EventSource` مرورگر نمی‌تواند هدر `Authorization` بفرستد، کلاینت باید از `fetch` + `ReadableStream` (یا کتابخانه‌ای که هدر می‌فرستد) استفاده کند. `EventSource` ساده با این endpoint کار نمی‌کند.
- SSE وابسته به Redis Pub/Sub است؛ در صورت قطع Redis، به polling برگردید.

#### ۵.۴ جایگزین Polling

- `GET /api/v1/storefront/orders/<id>/` هر ۱۰ تا ۱۵ ثانیه.
- یا `GET /api/v1/storefront/orders/?limit=20&offset=0` برای فهرست سفارش‌ها (صفحه‌بندی پیش‌فرض ۲۰).
- هر دو فقط سفارش‌های خود کاربر را برمی‌گردانند.

#### ۵.۵ درخواست لغو توسط مشتری

```
POST /api/v1/storefront/orders/<id>/request-cancellation/
Authorization: Bearer <access>

{ "reason": "دیگر نیازی ندارم" }
```

پیش‌شرط‌ها:

| شرط | نتیجه |
| --- | --- |
| سفارش مال کاربر نیست/وجود ندارد | `404 ORDER_NOT_FOUND` |
| `payment_status != PAID` | `409 INVALID_ORDER_STATE` |
| وضعیت `PROCESSING` یا `READY` نیست | `409 INVALID_ORDER_STATE` |
| قبلاً درخواست ثبت شده | `409 INVALID_ORDER_STATE` |

در موفقیت:

- `cancellation_requested = true`
- `cancellation_request_reason` و `cancellation_requested_at` ثبت می‌شوند
- پاسخ، سفارش به‌روزرسانی‌شده است
- رویداد `order.cancellation_requested` منتشر می‌شود

مهم:

- این endpoint سفارش را **لغو نمی‌کند** و پولی **برنمی‌گرداند**.
- تصمیم با مدیر است: او از Backoffice سفارش را لغو می‌کند → وضعیت `CANCELED` و `payment_status=AWAITING_REFUND`.
- بازپرداخت به‌صورت **دستی** (کارت‌به‌کارت) انجام و سپس با ثبت `card_number` و `tracking_code` در Backoffice وضعیت `REFUNDED` می‌شود.
- مشتری این تغییرات را با polling یا SSE می‌بیند.
- درخواست لغو برای سفارش `PENDING_PAYMENT` یا `COMPLETED` ممکن نیست.
- ثبت درخواست، مانع لغو توسط مدیر نمی‌شود.

#### ۵.۶ سفارش مجدد با یک کلیک

```
POST /api/v1/storefront/orders/<id>/reorder/
Authorization: Bearer <access>
```

پاسخ:

```json
{
  "items": [
    {
      "product_id": 10,
      "name": "پیتزا مارگاریتا",
      "quantity": 2,
      "unit_price": 190000,
      "addons": [
        { "addon_id": 3, "name": "پنیر اضافه", "quantity": 1, "unit_price": 20000, "line_total": 20000 }
      ],
      "line_total": 400000
    }
  ],
  "warnings": [
    "قیمت محصول «پیتزا مارگاریتا» تغییر کرده است."
  ]
}
```

قواعد:

- سفارش باید متعلق به همان کاربر باشد؛ وگرنه `404 ORDER_NOT_FOUND`.
- این endpoint **سفارش جدید نمی‌سازد** و سبد سروری هم نمی‌سازد؛ فقط اقلام را با قیمت‌های **فعلی** بازمی‌گرداند.
- فرانت باید خروجی را به سبد `localStorage` تبدیل کند و سپس `POST /orders/` بزند.
- وضعیت سفارش مبدأ مهم نیست؛ از هر سفارش قبلی (حتی لغوشده) می‌توان سفارش مجدد ساخت.
- بررسی باز بودن رستوران، کد تخفیف یا حداقل مبلغ در این مرحله انجام نمی‌شود؛ همه در `POST /orders/` اعمال می‌شوند.

قواعد هشدارها:

| وضعیت فعلی | رفتار | هشدار |
| --- | --- | --- |
| محصول حذف نرم شده | حذف از سبد | بله |
| محصول `OUT_OF_STOCK` یا `HIDDEN` | حذف از سبد | بله |
| دسته محصول حذف/غیرفعال | حذف از سبد | بله |
| قیمت محصول تغییر کرده | با قیمت جدید می‌آید | بله |
| افزودنی حذف‌شده/ناموجود/از محصول حذف‌شده | حذف افزودنی | بله |
| تعداد افزودنی از `max_quantity` بیشتر | به سقف جدید کاهش می‌یابد | بله |
| قیمت افزودنی تغییر کرده | با قیمت جدید می‌آید | بله |
| تعداد محصول تغییر کرده باشد | همان تعداد قبلی حفظ می‌شود | خیر |
| همه آیتم‌ها حذف شوند | `items: []` و چند هشدار | بله |

- هشدارها یکتا هستند (تکرار نمی‌شوند).
- `line_total` محاسبه‌شده در پاسخ صرفاً نمایشی است؛ مبلغ نهایی در ثبت سفارش دوباره از سرور محاسبه می‌شود.

#### ۵.۷ حالت‌های مرزی سناریو ۵

| سناریو | رفتار |
| --- | --- |
| اتصال SSE بدون توکن | `401` |
| اتصال SSE به سفارش کاربر دیگر | `404` |
| قطع و وصل مجدد SSE | رویدادهای گذشته بازپخش نمی‌شوند؛ باید دوباره `GET /orders/<id>/` بزنید |
| SSE وقتی Redis قطع است | فریم `: error` و بسته شدن استریم |
| درخواست لغو دوم | `409` |
| درخواست لغو برای سفارش پرداخت‌نشده | `409` |
| لغو توسط مدیر پس از درخواست مشتری | `CANCELED` + `AWAITING_REFUND` |
| بازپرداخت دستی ثبت شود | `REFUNDED` |
| سفارش مجدد از سفارش لغوشده | مجاز |
| سفارش مجدد وقتی همه محصولات ناموجودند | `items: []` با هشدارها |
| تغییر قیمت بعد از ساخت سبد | در `POST /orders/` قیمت جدید ملاک است؛ قیمت کلاینت هرگز پذیرفته نمی‌شود |

## پیوست ج — چک‌لیست اتصال فرانت‌اند

1. **توکن‌ها:** `access` و `refresh` را در حافظه امن نگه دارید؛ کوکی ورود وجود ندارد.
2. **Refresh:** در `401 TOKEN_NOT_VALID` یک‌بار refresh کنید و درخواست را تکرار کنید؛ از حلقه بی‌پایان جلوگیری کنید.
3. **چرخش:** پس از هر refresh، هر دو توکن جدید را جایگزین کنید؛ refresh قدیمی باطل می‌شود.
4. **خروج:** هم `refresh` را به `/auth/token/logout/` بدهید و هم توکن‌های محلی را پاک کنید؛ `access` تا انقضا زنده است.
5. **سبد:** در `localStorage`؛ هیچ API سبد وجود ندارد. در Checkout از `product_id`, `quantity`, `addon_id`, `quantity` استفاده کنید، نه قیمت.
6. **آدرس:** قبل از `DELIVERY` وجود آدرس را تضمین کنید؛ سقف ۴ آدرس و مسیر `replace_address_id` را در UI پیش‌بینی کنید.
7. **کد تخفیف:** قبل از پرداخت، `validate-promo` را صدا بزنید؛ مقدار `subtotal` را از سبد محاسبه کنید. بعد از هر تغییر سبد دوباره اعتبارسنجی کنید.
8. **پرداخت:** مبلغ را از پاسخ سرور نمایش دهید؛ پس از بازگشت از درگاه، نتیجه را از query string صفحه نتیجه بخوانید و برای اطمینان `GET /orders/<id>/` بزنید.
9. **پیگیری:** ابتدا وضعیت فعلی را با `GET /orders/<id>/` بگیرید، سپس SSE را با `fetch` و هدر `Authorization` باز کنید؛ در قطعی به polling برگردید.
10. **لغو:** درخواست لغو به معنی لغو نیست؛ وضعیت `AWAITING_REFUND`/`REFUNDED` را از داده سفارش نمایش دهید.
11. **سفارش مجدد:** خروجی `reorder` را به سبد تبدیل کنید و هشدارها را به کاربر نشان دهید؛ قیمت‌ها ممکن است تغییر کرده باشند.
12. **خطاها:** همیشه `error.code` را برای منطق و `error.message` را برای نمایش استفاده کنید؛ `details` ساختار ثابت ندارد.
